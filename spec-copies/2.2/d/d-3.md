# D.3: performance

Do not start this spec until every rule in D.1 and D.2 passes.

## Tips

- **Do not block the event loop.** Run SQLite calls in a thread (FastAPI does this for plain `def`
  routes), or one slow query holds up every WebSocket on that node.
- **Keep transactions short.** Use WAL mode and a `busy_timeout`, and hold `BEGIN IMMEDIATE` only
  while writing.
- **Share the table check.** One task per node reads new events and hands them to subscribers,
  rather than each WebSocket reading the database on its own.

## Uses

Call these functions from earlier parts of the app. Do not write a second version of any of them.

| Function | Used here for |
|---|---|
| `post_message(...)`, `emit_event(channel_id, type, payload)` | The writes being measured |
| `ws_endpoint` at `/api/ws` | The deliveries being measured |

## Adds

Nothing new is required. Change the code above if the rules fail.

## Rules

Six clients subscribe to one channel, two on each node. Nine writers, three on each node, post 30
messages each, waiting 100 ms after each `201`. Latency runs from just before the `POST` is sent
until a subscriber gets that message's `message.created` frame, and is worked out for each
subscriber.

3.1 **Median.** Every subscriber's median latency is at most `300 ms`.

3.2 **p95.** Every subscriber's p95 latency is at most `800 ms`.

3.3 **Missing events.** At most `1%` of the expected frames are missing, counting every subscriber
    and every message. A write that does not return `201` counts as missing for every subscriber.
