# D.1: a killed HTTP node

## Tips

- **Supervise from `start.sh`.** Start each node, save its PID, and stay in a loop that checks each
  saved PID with `kill -0` and starts that node again if it is gone, with the same `node_id` and
  port. `start.sh` itself never exits.
- **Keep everything shared in the database.** Users, tokens, messages and events must be in the one
  database file, so that a node that restarts or a client that moves to another node loses nothing.
- **No node is special.** No node may depend on another node to read, write or send events.
- Kill only by a PID you saved or the PID that owns a port (`ss -ltnp`), never by name.

## Uses

Call these functions from earlier parts of the app. Do not write a second version of any of them.

| Function | Used here for |
|---|---|
| `post_message(...)`, `emit_event(channel_id, type, payload)` | Writes, and the next `event_id` |
| `ws_endpoint` at `/api/ws` | `subscribe` and `resume` on any node |

## Adds

| Function | What it does |
|---|---|
| The loop in `/app/start.sh` | Starts any HTTP node that has died again |

## Rules

In these rules one HTTP node gets `SIGKILL`, using the PID that owns its port. `start.sh` is left
running. WebSocket subscribers are connected to all three nodes before the kill.

1.1 **Reads and writes.** Right after the kill, the other two nodes answer `GET
    /api/channels/{id}/messages` and `POST /api/channels/{id}/messages`. A message written on the
    killed node before the kill is still listed. A message written on one surviving node is listed
    on the other.

1.2 **WebSocket delivery.** A subscriber on a surviving node stays connected, and gets a
    `message.created` frame for a message written on the other surviving node within 3 seconds.

1.3 **Replay.** A client that lost its WebSocket when the node died connects to a surviving node
    and sends `{"type": "resume", "channel_id": <id>, "since_event_id": <n>}`, where `n` is the last
    `event_id` it had. It gets every later event in order, then `{"type": "resumed", "channel_id":
    <id>, "head_event_id": <latest>}`.

1.4 **The node comes back.** Without anyone doing anything, the killed node answers
    `GET /api/health` with `200` and its own `node_id` within 15 seconds.

1.5 **All three again.** After it comes back, tokens issued before the kill still work on that
    node, and it lists the messages written while it was down. A message written on each of the
    three nodes reaches subscribers on all three nodes within 4 seconds, and the channel's
    `event_id` values have no gaps and no repeats since before the kill.

Every request must answer within 5 seconds.
