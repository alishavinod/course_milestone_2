# D.2: a killed Redis

Do not start this spec until every rule in D.1 passes.

## Tips

- **Run the real daemon.** `start.sh` runs `redis-server --port 6379 --bind 127.0.0.1 --save ""
  --appendonly no`, saves its PID, and starts it again from the same loop as the nodes. List
  `redis` in `/app/requirements.txt` if you use the Python client.
- **Redis is only a signal.** `event_id` and the events themselves stay in the database. Redis tells
  the other nodes to look sooner. Each node also keeps checking the events table about every 100 ms,
  so events still arrive when Redis is down.
- **A failed publish must not fail the write.** Commit first, then publish. Use a short socket
  timeout and ignore connection errors.
- **Reconnect.** Each node has a background listener that retries its Redis connection and
  subscribes again, forever.
- **Send each event once.** A signal and a table check can both find the same event, so remember
  the last `event_id` sent to each subscriber.

## Uses

Call these functions from earlier parts of the app. Do not write a second version of any of them.

| Function | Used here for |
|---|---|
| `emit_event(channel_id, type, payload)` | Publishes a signal after the commit |
| `ws_endpoint` at `/api/ws` | Sends new events to subscribers |
| The loop in `/app/start.sh` | Also starts Redis again |

## Adds

| Function | What it does |
|---|---|
| `publish_event(channel_id, event_id)` | Tells the other nodes about a new event, ignoring Redis errors |
| `redis_listener()` | On each node: subscribes, wakes up subscribers, and reconnects after a failure |

## Rules

In these rules a client is subscribed to a channel on each of the three nodes.

2.1 **Redis runs and is used.** `127.0.0.1:6379` answers `PING` with `PONG`. Redis `CLIENT LIST`
    shows at least 3 connections with a pub/sub subscription, at least one for each node. Each node
    process holds its own subscription; a separate process such as `redis-cli` does not count.

Then the process that owns port `6379` gets `SIGKILL`. Rules 2.2 to 2.4 start right away.

2.2 **Writes keep working.** Messages written on each of the three nodes return `201`, starting
    immediately after the kill.

2.3 **Delivery keeps working.** Every subscriber on every node gets a `message.created` frame for
    each of those messages within 5 seconds of the kill.

2.4 **Dense `event_id`.** Each subscriber's `event_id` values continue from its `head_event_id`
    with no gaps and no repeats.

2.5 **Redis comes back.** Without anyone doing anything, `127.0.0.1:6379` answers `PING` again
    within 10 seconds of the kill.

2.6 **Pub/sub resumes.** Within 5 seconds of that, `CLIENT LIST` again shows a subscribed
    connection for each node. A message written on each node reaches subscribers on all three nodes, and
    `event_id` still has no gaps and no repeats.

Every request must answer within 5 seconds.
